# Campus OS — Central Institute of Technology

An AI-native, offline-first digital campus management prototype, built for
the **Smart University Digital Campus** challenge (MPOnline Idea & Innovation
Hackathon 2026). See `README.md` for the pitch/demo-script framing ("three
moats": AI that acts, offline-first, legacy-compatible import). This file is
the technical map for a future coding session working in this repo.

## Two processes, one repository

This used to be a single Next.js app that talked to a local SQLite file
directly from its API routes. That broke the moment it was deployed to
Vercel — serverless functions get a read-only filesystem and a native
binary (`better-sqlite3`) built for a different platform than the one it
runs on, so every page 500'd. Rather than patch around that, the backend
was pulled out entirely:

```
frontend/  (repo root: app/, lib/, components/)   →  Vercel
backend/   (Rust + Axum)                          →  anywhere with a Linux box and Postgres
```

Both halves live in this one git repo — there was never a reason to split
it into two. `backend/` has its own `Cargo.toml`/`DEPLOY.md` and is
`.vercelignore`d from the frontend's build.

```
Browser
  │  same-origin fetch (lib/client/api.ts — unchanged)
  ▼
Next.js on Vercel (pages + one catch-all API proxy + the AI routes)
  │  server-to-server HTTPS, cookie forwarded as-is
  ▼
Rust (Axum) backend — standalone binary, deployed separately (backend/)
  │
  ▼
PostgreSQL
```

The backend is plain `axum` + `sqlx` + `tokio` talking to Postgres over a
`DATABASE_URL` env var — no AWS SDK, no cloud-specific service calls
anywhere in it. The same binary/Docker image runs on an EC2 box, another
cloud, or a college's own server room; see `backend/DEPLOY.md` for both a
Docker-on-EC2 path and a plain systemd-on-bare-metal path. That
"legacy-compatible" story — it runs on the same kind of tin these
institutions already have, not just modern serverless — is the point.

## Why a catch-all proxy instead of per-route rewrites

`app/api/[...path]/route.ts` is the only Next.js API route left besides
`/api/ai/chat` and `/api/ai/act`. It forwards method, the `campus_demo_user`
cookie, query string and body to `${BACKEND_URL}<path>` and relays back
status/JSON/`Set-Cookie` verbatim (see the `NO_BODY_STATUSES` handling in
that file — the Fetch `Response` constructor throws if you pass a body
alongside a 204/205/304, which bit the logout flow once already). Because
this is a server-to-server call (a Vercel function calling the Rust
backend), there's no CORS or cross-site-cookie problem to solve.

This means adding or changing a backend domain **never touches the
frontend** — the moment an Axum handler exists at a given path, the proxy
already serves it. `lib/client/api.ts`, `use-api.ts`, the IndexedDB offline
cache and outbox are all unchanged from before the split; they only ever
knew about same-origin `/api/...` paths.

`proxy.ts` (the Next.js page-level login gate, cookie-presence only) is
unaffected — it never touched the database.

## Tech stack

**Frontend** (repo root): Next.js **16.3.5** (App Router, Turbopack) ·
React 19.2.8 · TypeScript · Tailwind CSS v4 · Base UI (wrapped shadcn-style

**Backend** (`backend/`): Rust · Axum · `sqlx` (async, Postgres, compile-time

· Tokio · PostgreSQL.

**Next.js 16 is newer than most training data** — `node_modules/next/dist/docs/`
has the bundled docs; `AGENTS.md` (auto-regenerated by `next dev`, don't hand-edit
its marker block) points here. The one that bit during the original build:
`middleware.ts` is deprecated → renamed `proxy.ts` in v16 (same behavior).
Route handler dynamic segments take `{ params }: { params: Promise<{ id: string }> }`.

## Login / session

- **`/login`** (`app/login/page.tsx`) is a standalone page with a dropdown
  of every seeded demo persona, grouped by category and labeled with their
  assigned role name(s). No password, by design. It posts `{userId}` to
  `POST /api/demo/session` (proxied straight to the backend, which sets the
  cookie and returns the `ClientContext`) and redirects to `?next=` or `/`.
- **`proxy.ts`** redirects any page request with no `campus_demo_user`
  cookie to `/login?next=<path>`. **UX convenience only** — it can't
  cheaply validate the cookie against the DB, so it never replaces the real
  check.
- **The real check** is the backend's `Session` extractor
  (`backend/src/auth.rs`): every protected Axum handler takes
  `Session(ctx): Session` as a parameter, which reads the cookie, loads the
  caller's full `AccessContext` (grants, scope-relevant identity) from
  Postgres, and 401s via `AppError::Unauthenticated` if the cookie is
  missing or points at a user that no longer exists. There is no
  per-route opt-in — a handler either takes `Session` and is protected, or
  it doesn't.
- **Server Components** (the root layout, `app/page.tsx`, the four
  persona dashboards) call `lib/server-context.ts`'s
  `getCurrentClientContext()` / `getCurrentClientContextOrNull()`, which
  fetch `GET /api/profile` from the backend with the request's cookies
  forwarded, instead of hitting a local DB. `backendGet<T>(path)` in the
  same file is the general-purpose version other Server Components (the
  admin/faculty dashboards) use to pull their own data server-side.
- **Client-side**: `useSession().logout()` calls `DELETE /api/demo/session`
  (proxied), clears the IndexedDB offline cache, and routes to `/login`.

## The backend (`backend/`)

```
backend/
  Cargo.toml
  migrations/0001_init.sql     full Postgres schema, one file, 36 tables
  .sqlx/                       checked-in offline query-check cache (see below)
  src/
    main.rs                    wires the router, runs migrations on boot
    config.rs                  COOKIE_NAME, the permission catalog, legacy-role-map
                                defaults — the "hardcoded values, separate file"
    error.rs                   AppError → {"error": msg} + status, matches the
                                old lib/api-helpers.ts contract exactly
    state.rs                   AppState { pool, import_jobs } (Clone, cheap)
    auth.rs                    load_context(), the Session extractor
    rbac/                      permissions.rs data lives in config.rs; scope.rs,
                                grants.rs, authorize.rs, audit.rs are the direct
                                port of the original lib/rbac/*.ts engine
    routes/                    one file per domain — students.rs, attendance.rs,
                                exams.rs, fees.rs, rbac_admin.rs, import_data.rs...
                                each owns both its Axum handlers and whatever
                                query logic backs them (no separate "service
                                layer" — nothing else in Rust calls these
                                functions, so there was nothing to decouple for)
  Dockerfile / docker-compose.yml / deploy/campus-backend.service / DEPLOY.md
```

Business logic and authorization now live entirely here — `lib/services/*`,
`lib/rbac/*`, `lib/db/*`, `lib/demo-session.ts` and `lib/api-helpers.ts` are
gone from the Next.js app. The same non-negotiable rule from the old
architecture still holds, just in the new location: **every handler that
touches protected data takes `Session(ctx)` and calls `authorize()` (or
`resolve_student_id_for_access()`, which calls it) before reading or
writing anything — never branch on `ctx.role` directly.**

### sqlx's offline mode

`sqlx::query!`/`query_as!` macros validate every SQL string against a real
schema at *compile time* — great for correctness, but it means `cargo
build` normally needs a live `DATABASE_URL`. That's unavailable in a Docker
build or CI. The fix: `cargo sqlx prepare` (from `sqlx-cli`) writes query
metadata into `.sqlx/`, which is checked into git; building with
`SQLX_OFFLINE=true` (set in the `Dockerfile`) uses that cache instead of a
live connection. **Whenever a query changes, re-run `cargo sqlx prepare`**
(with a real `DATABASE_URL` pointed at a migrated local Postgres) and
commit the resulting `.sqlx/` diff, or the next offline build will use
stale query shapes.

### Local development

```
brew install postgresql@16                 # once

```

Then from the repo root: `cp .env.example .env.local` (set
`BACKEND_URL=http://localhost:4000`) and `npm run dev` as before.

### Demo data

The backend doesn't generate its own fake data — the original ~1300-line
TypeScript seed generator (`lib/db/seed.ts`) was SQLite/Drizzle-specific and
didn't port over. Instead, `data/campus.db` (the already-seeded SQLite
snapshot from the old architecture — ~1500 students, all domains, RBAC
roles/demo users) is kept in the repo as a frozen fixture, and
`npm run migrate-demo-data` (`scripts/migrate-sqlite-to-postgres.ts`) copies
every table from it into whatever Postgres `DATABASE_URL` points at, in
FK-safe order. Run it once against a freshly-migrated database. If you ever
need genuinely fresh random demo data rather than this fixed snapshot,
that generator would need to be rewritten against Postgres — it doesn't
exist today.

## Data model

The schema is unchanged in shape from the original design — it just lives
in `backend/migrations/0001_init.sql` (Postgres DDL) now instead of
`lib/db/schema.ts` (Drizzle/SQLite). Institution structure: `universities`
→ `departments` → `programmes` → `courses` → `sections` →
`timetable_slots`. People: `students`, `faculty`, `parents`, `employees`,
`users` (the login/identity row — not a real auth table, no passwords).
Academics: `attendance`, `exams`, `exam_results` (`graded` boolean doubles
as the "published to student" flag). Finance: `fees`, `payments`. Campus
services: `documents`/`certificates`, `hostels`/`rooms`/`room_assignments`,
`transport_*`, `helpdesk_tickets`/`ticket_messages`, `notifications`,
`books`/`book_loans`, `scholarships`/`scholarship_applications`. Import:
`import_jobs`. RBAC: `roles`, `role_permissions`, `user_roles`,
`audit_logs`, `legacy_role_mappings`.

## AI assistant (lib/ai/)

`aiProvider` (`lib/ai/engine.ts`) still picks `GroqProvider` if
`GROQ_API_KEY` is set, else the deterministic `RuleBasedProvider` — same
`AIProvider` interface, same `AssistantMessage` shape, so the UI never
knows which is active. What changed: the AI stayed in Next.js/Node (the
Groq SDK and the regex-based rule matching have no reason to move to
Rust), but its tools no longer call service functions in-process — there's
no DB to call into anymore. `lib/ai/tools.ts`'s `run(caller, args)` now
does `backendFetch(caller.cookie, "/api/...")` for every tool, forwarding
the same session cookie the chat/act routes received. `lib/ai/backend.ts`
is that fetch wrapper plus `loadCaller()` (builds a `Caller` — the cookie
plus the `ClientContext` from `GET /api/profile`) and `BackendError` (the
`AccessDeniedError` replacement — a 403 from the backend, caught the same
way `AccessDeniedError` used to be, to produce the generic "I don't have
access to that information for your account." reply rather than leaking
which record was denied).

`format-tool-result.ts` is untouched — it only ever looked at a tool's
*result shape*, never at how that result was fetched, so nothing there
needed to change.

## Offline-first (lib/client/, lib/offline/)

Completely unchanged by the backend split — `apiGet`/`apiMutate` only ever
talked to same-origin `/api/...` paths and had no idea a local DB used to
answer them. Per-user IndexedDB cache/outbox namespacing, the network-mode
simulator, and `useSyncStatus`'s outbox flush (which replays queued writes
as real `fetch()` calls so the server re-authorizes fresh) all work exactly
as before.

## Legacy import (backend/src/routes/import_data.rs, /admin/import)

The pipeline (parse → heuristic column mapping → validate → commit) now
lives entirely in the Rust backend: `csv`/`calamine` crates parse
CSV/XLSX, `serde_json` parses JSON, and an in-memory `Mutex<HashMap<String,
ImportJob>>` on `AppState` holds parsed rows between the upload and
commit steps (matches the original's in-memory job store — this backend is
a persistent long-lived process, not a serverless function, so that's a
legitimate design here). `lib/importer/mapping.ts`'s heuristic
column-similarity scoring (exact match, prefix/substring, then token
overlap) was ported line-for-line into
`backend/src/routes/import_data.rs::infer_mapping`. The RBAC-side "legacy
role mapping" table (mapping a legacy system's staff-role labels onto this
app's roles) is a separate, purely additive feature, not wired into this
student-CSV pipeline.

## RBAC & authorization

The mental model is unchanged — this section describes the same engine,
now implemented in `backend/src/rbac/*.rs` instead of `lib/rbac/*.ts`.

```
USER -> ROLE(S) -> PERMISSIONS -> SCOPE CHECK -> DATA
```

- **Permissions are stable strings** (`resource.action`), catalogued once
  in `backend/src/config.rs`'s `PERMISSIONS` const (key, label,
  description, group, sensitive) — the only place a new permission key
  gets invented.
- **Roles are DB rows** (`roles`/`role_permissions`/`user_roles` tables),
  fully editable at runtime from `/admin/rbac`.
- **A user can hold multiple roles.** Each assignment carries an optional
  explicit `scope` (JSON: `{"all":true}` or `{"departmentId":3}`). When
  `scope` is `null`, `resolve_dynamic_scope()`
  (`backend/src/rbac/authorize.rs`) resolves it from the caller's own
  identity at request time — same table as before:

  | `need` shape     | Student           | Parent                          | Faculty                                                             |
  |------------------|-------------------|-----------------------------------|------------------------------------------------------------------------|
  | `studentId`      | their own id      | their child (`parents.student_id`) | any student in their course rosters (`sections.faculty_id` → programme+semester match) |
  | `courseId`       | n/a               | n/a                                | any course they teach (`sections.faculty_id`)                          |
  | `departmentId`   | n/a               | n/a                                | `ctx.department_id`                                                     |

- **The single entrypoint is `authorize(pool, ctx, permission, need, opts)`**
  (`backend/src/rbac/authorize.rs`): checks the caller holds the
  permission, checks scope against `need` if given, audits every denial
  and every sensitive-permission success, and returns
  `Err(AppError::AccessDenied)` on failure (mapped to HTTP 403 by
  `error.rs`). `can(pool, ctx, permission, need)` is the non-throwing,
  non-auditing read-only variant — **never use `can()` for an actual
  security decision.** `resolve_student_id_for_access()` (most
  student-scoped handlers call this) picks the target student id
  (explicit, or the caller's own/child id) and calls `authorize()` under
  the hood.
- One difference from the old implementation, worth knowing: the original
  TS `AccessContext` memoized dynamic-scope lookups per-request on a
  `_cache` Map. The Rust port doesn't — each `authorize()` call resolves
  scope fresh. At this dataset's scale that's a handful of extra indexed
  queries per request, not a real cost; if that ever matters, that's the
  thing to add back.

### Exam-results publish gate

Unchanged: `exam_results.graded` doubles as the "published" flag. Faculty
entering/editing marks (`backend/src/routes/exams.rs::enter_marks`) sets
`graded=false`; `publish_results` (Examination Department,
`exam.results.publish`) flips it to `true`. Students/parents only ever see
`graded=true` rows.

### Demo logins

Unchanged — pick one from the `/login` dropdown, or
`POST /api/demo/session {"userId": N}` directly; full list at
`GET /api/demo/users`. See the original README for the exact spec-aliased
and CIT-branded accounts, and the department-role accounts
(`hod@demo.college`, `accounts@demo.college`, etc.).

### How to extend

- **New permission**: add one entry to `PERMISSIONS` in
  `backend/src/config.rs`. Grant it via `/admin/rbac` → Roles &
  Permissions → toggle → Save (no seed-template mechanism exists anymore —
  see "Demo data" above — so a brand-new install needs this done through
  the UI or a manual `role_permissions` insert after migrating demo data).
- **New role**: `/admin/rbac` → "New role", check its permissions. No code
  change.
- **New scoped resource type**: extend `Scope`/`ResourceNeed`
  (`backend/src/rbac/types.rs`), handle it in `scope_allows()`
  (`scope.rs`), add a branch in `resolve_dynamic_scope()`
  (`authorize.rs`) if it should fall back to the caller's own identity.

### Known gaps (deliberately out of scope)

- No assignments/study-materials feature exists — same as before, the
  spec's `assignment.*`/`study_material.*` permissions are catalogued for
  completeness but nothing enforces or renders them.
- Admission Cell is a lightweight "recent admissions + onboard student"
  view, not a full applications/leads pipeline.
- `exam.marks.manage`/`exam.application.manage`/`exam.schedule.manage` are
  granted to the Examination Officer role but only
  `exam.results.publish`/`exam.results.manage` have real handlers behind
  them.
- Payments run in demo mode only — `backend/src/routes/payments.rs`
  creates a `demo_order_*` order and signature-verifies it locally; it
  never calls out to a real Razorpay API (the original TS version did,
  when `RAZORPAY_KEY_*` were set — that real-order-creation path wasn't
  ported, since porting it would mean pulling in an HTTP client crate for
  a code path this deployment never actually exercises). The real-signature
  HMAC verification path (for a payment that *did* go through a real
  gateway) is still there, just not order creation.
- The frontend's old per-request scope memoization doesn't exist in the
  Rust port — see the RBAC section above.
