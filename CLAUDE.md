# Campus OS — Central Institute of Technology

An AI-native, offline-first digital campus management prototype, built for
the **Smart University Digital Campus** challenge (MPOnline Idea & Innovation
Hackathon 2026). See `README.md` for the pitch/demo-script framing ("three
moats": AI that acts, offline-first, legacy-compatible import). This file is
the technical map for a future coding session working in this repo —
architecture, conventions, where things live, and non-obvious decisions.

The README's demo-account table predates the RBAC work below and only lists
the original 4 accounts — the full, current list of ~20 seeded logins is in
the RBAC section further down.

## Tech stack

Next.js **16.3.5** (App Router, Turbopack) · React 19.2.8 · TypeScript ·
Tailwind CSS v4 · Base UI (wrapped shadcn-style in `components/ui/*`) ·
Drizzle ORM + better-sqlite3 (`data/campus.db`) · Zod · Dexie (IndexedDB) ·
Recharts · Lucide icons · Groq SDK (optional LLM) · Razorpay (optional
payments) · Papaparse/xlsx (legacy import).

**Next.js 16 is newer than most training data** — `node_modules/next/dist/docs/`
has the bundled docs; `AGENTS.md` (auto-regenerated by `next dev`, don't hand-edit
its marker block) points here. The one that bit during this work:
`middleware.ts` is deprecated → renamed `proxy.ts` in v16 (same behavior).
This project doesn't use either — security is enforced entirely in the
service layer (see below), matching Next's own Data Access Layer guidance,
not in a proxy/middleware file. Route handler dynamic segments take
`{ params }: { params: Promise<{ id: string }> }` (`params` is now a Promise).

## Architecture

```
UI (Next.js App Router; "use client" pages fetch via lib/client/api.ts)
  │
  ├─ AI layer         lib/ai/{engine,groq-provider,tools,provider}.ts
  │                    same tool registry either way - deterministic rule-based
  │                    NLU when GROQ_API_KEY is unset, real LLM tool-use when set
  │

  │                     every read/write goes through here; authorization is
  │                     enforced HERE, not in route handlers, not in the UI
  │

  │
  ├─ Drizzle ORM        lib/db/schema.ts → SQLite (data/campus.db)
  │
  └─ Importer          lib/importer/{adapters,mapping}.ts
```

## Login / session (proxy.ts, /login)

There's a real "logged out" state now — this used to be a topbar dropdown
that silently switched identity with no concept of "not signed in" at all
(`getCurrentContext()` fell back to a default student user if the cookie was
missing). That's gone:

- **`/login`** (`app/login/page.tsx`) is a standalone page (no sidebar/topbar
  chrome) with a single dropdown of every seeded demo persona, grouped by
  category (Student/Parent/Faculty/Administrator/Department staff) and
  labeled with their assigned role name(s) — e.g. "Ansh Pandey — Faculty +
  Head of Department". No password, by design (this is a prototype demo). It
  posts `{userId}` to `POST /api/demo/session` and redirects to `?next=`
  (set by proxy below) or `/`.
- **`proxy.ts`** (project root — Next 16 renamed `middleware.ts` → `proxy.ts`,
  see the top of this file) redirects any page request with no
  `campus_demo_user` cookie to `/login?next=<path>`, and redirects away from
  `/login` if the cookie is already present. **This is a UX convenience
  only** — it doesn't (and can't, cheaply) validate the cookie against the
  DB, so it never replaces the real check. It's excluded from `/api/**`,
  `_next/static|image`, and the PWA files (`sw.js`, `manifest.webmanifest`,
  `/samples/*`) via its `matcher`.
- **The real check** is `getCurrentContext()` (`lib/demo-session.ts`):
  throws `UnauthenticatedError` if the cookie is missing *or* points at a
  deleted/stale user (e.g. after a reseed) — mapped to **401** by
  `lib/api-helpers.ts`. Every API route already calls this inside its
  standard try/catch, so this needed zero per-route changes. Server
  Component pages call it directly and would surface Next's error boundary
  if reached with no session — acceptable as a defense-in-depth path since
  `proxy.ts` is the real gate for pages.
- **`getCurrentContextOrNull()`** / **`getCurrentClientContextOrNull()`** are
  for the one place that must render *something* either way: the root
  layout (`app/layout.tsx`) reads this and passes `ClientContext | null` into
  `AppProviders` — `null` renders `children` bare (used by `/login`),
  non-null wraps them in `SessionProvider` + `AppShell` as before.
- **Logging in/out**: `lib/demo-session.ts` exports `loginAsUser(userId)`
  (sets the cookie, records an `auth.login` audit entry) and `logout()`
  (clears the cookie, records `auth.logout`). Client-side,
  `useSession().logout()` (`lib/client/session.tsx`) calls
  `DELETE /api/demo/session`, clears the IndexedDB offline cache (see
  Offline-first), and routes to `/login`. `ProfileMenu` no longer has a
  user-switcher — just identity display + "Log out". To pick a different
  persona now, log out and use the `/login` dropdown.
- A previously-latent bug got fixed while touching this: the root layout
  used to pass the full server-only `AccessContext` (including `grants` and
  the `_cache` Map) straight into a Client Component prop — it now always
  goes through `toClientContext()`/`getCurrentClientContextOrNull()` first.

## Everything funnels through the service layer

**API routes are intentionally thin** — the universal shape is:
```ts
export async function GET(req: Request) {
  try {
    const ctx = await getCurrentContext();      // lib/demo-session.ts
    const data = await someService.doThing(ctx, ...args);
    return NextResponse.json(data);
  } catch (err) {
    return handleApiError(err);                  // lib/api-helpers.ts -> 403 on AccessDeniedError
  }
}
```
Never put business logic or authorization checks in a route handler — add a
function to the relevant `lib/services/*.ts` file instead. This is also why
there's no `proxy.ts`: a route/page-level gate would only be UX, and the
Next.js data-security guide is explicit that Server Actions/route handlers
are independently reachable and must each re-authorize.

**Client-side data fetching**: `useApiGet(path)` (`lib/client/use-api.ts`)
for reads, `apiMutate(path, opts)` (`lib/client/api.ts`) for writes. Both are
offline-aware (see Offline-first section) — don't `fetch()` directly from a
component.

## Data model (lib/db/schema.ts)

Institution structure: `universities` → `departments` → `programmes` →
`courses` → `sections` (a course taught by one `faculty` member) →
`timetable_slots`.

People: `students`, `faculty`, `parents` (→ `studentId`), `employees`
(non-teaching staff: Accounts/Admission/HR/Examination/Library/Maintenance/
Placement/IT), `users` (login/identity row — maps a person to at most one of
student/faculty/parent/employee, plus a legacy `role` display column). `users`
is **not** a real auth table (no passwords) — it's how the demo-session cookie
resolves "who is this".

Academics: `attendance`, `exams`, `exam_results` (`graded` boolean doubles as
the "published to student" flag — see RBAC section), `timetable_slots`.

Finance: `fees`, `payments` (Razorpay order/payment ids, falls back to a
"demo mode" order id when `RAZORPAY_KEY_ID`/`SECRET` aren't set).

Campus services: `documents`/`certificates`, `hostels`/`rooms`/
`room_assignments`, `transport_routes`/`transport_stops`/
`transport_assignments`, `helpdesk_tickets`/`ticket_messages`,
`notifications`, `books`/`book_loans`, `scholarships`/
`scholarship_applications`.

Import: `import_jobs` (tracks legacy CSV/XLSX/JSON imports).

RBAC: `roles`, `role_permissions`, `user_roles`, `audit_logs`,
`legacy_role_mappings` — see below.

`sqlite.pragma("foreign_keys = ON")` in `lib/db/client.ts` means **delete
order in `lib/db/seed.ts` matters** — child tables must be deleted before the
parents they reference. The existing order is already correct; if you add a
new table with a foreign key, insert its delete statement before whatever it
references.

## Feature modules (lib/services/*.ts)

Each file is a self-contained domain; API routes under `app/api/**` are thin
wrappers around these. Notable ones:

- **students.ts / faculty.ts** — profile lookups, directory search (admin/
  faculty), faculty's own courses/roster (`sections.facultyId` is the source
  of truth for "which courses does this faculty member teach").
- **attendance.ts** — `getAttendanceSummary` (read, any role via scope) +
  `markAttendance` (faculty write, scoped to their own courses).
- **exams.ts** — exam schedule (read), `enterMarks`/`getResultsForExam`
  (faculty write, scoped to their own courses), `publishResults`/
  `listExamsForPublishing` (Examination Department), `getMyResults`
  (student/parent read, published-only).
- **fees.ts / payments.ts** — student fee status + online payment
  (Razorpay or demo-mode), plus Accounts-Department-facing
  `getFinanceOverview`/`listFeeRecords`/`collectFeePayment` (manual/desk
  collection, separate from the student's own online-payment flow in
  `payments.ts`).
- **risk.ts** — computed (not stored) attendance/marks/fees/tickets risk
  score per student, used by dashboards, the "at-risk students" AI query, and
  scholarship eligibility checks.
- **admission.ts** — Admission Cell: recent admissions ledger +
  `onboardStudent` (creates a real `students` row). Deliberately lightweight —
  see "Known gaps" below.
- **employees.ts** — HR staff directory, combines `faculty` + `employees`.
- **import.ts** — legacy CSV/XLSX/JSON → canonical `students` rows, using
  `lib/importer/mapping.ts`'s heuristic column-similarity scoring (not an
  LLM call today, but returns the same `{column, canonicalKey, confidence}`
  shape one would, so swapping in a real model call later doesn't touch the
  pipeline or UI).
- **admin.ts / dashboard.ts** — aggregate overview stats for the admin home
  page and the student/parent dashboard respectively.

## AI assistant (lib/ai/)

`aiProvider` (`lib/ai/engine.ts`, bottom) picks `GroqProvider` if
`GROQ_API_KEY` is set, else `RuleBasedProvider` — **both implement the same
`AIProvider` interface and produce the same `AssistantMessage` shape** (text +
`cards` + `actions` + `toolTrace`), so the UI never knows which is active.

- **`tools.ts`** is the single tool registry both providers call into. Every
  tool's `run(ctx, args)` calls a service-layer function — the AI has no
  separate data path and no raw DB/SQL access. Tools marked `sensitive:true`
  (creating a ticket, notifying students/parents, applying for a
  scholarship) never execute directly from a raw LLM tool-call; they're
  intercepted and turned into a confirm button
  (`encodePendingAction`/`decodePendingAction`, executed later via
  `executePendingAction` / `POST /api/ai/act`).
- **`format-tool-result.ts`** turns a raw tool result into the same UI cards
  (`AICard`: table/stat/checklist/certificate/risk) the rule-based provider
  hand-builds, so an LLM-driven conversation renders identically to the
  deterministic one. **Any new case here must tolerate a denied `{error}`
  result** — a permission-checked tool can fail that way for any caller now
  (see the RBAC section for a bug that was fixed here).
- **`RuleBasedProvider`** (in `engine.ts`) matches intent by regex over the
  raw message and calls one of several `handle*` functions, each of which
  calls 1-3 tools and hand-assembles the reply/cards. It's a genuine fallback
  — not a stub — used whenever no Groq key is configured (e.g. this repo's
  local dev by default).
- Denial messages shown to the end user are always generic ("I don't have
  access to that information for your account.") — never a raw
  `AccessDeniedError.message`, and the system prompt tells the model to
  relay a tool's `error` field verbatim rather than speculate.

## Offline-first (lib/client/, lib/offline/)

- `lib/client/network.tsx` / `network-store.ts` — a manual network-mode
  simulator (Online / Slow / Offline), driven by the topbar switcher, backed
  by a plain module-level variable + `localStorage` (not React context, so
  non-component code like `api.ts` can read it).
- `lib/client/api.ts` — `apiGet` caches successful GETs into IndexedDB
  (`lib/offline/db.ts`, via Dexie) keyed by request path, and serves from
  that cache when mode is Offline. `apiMutate` queues writes into an IndexedDB
  outbox when `offlineCapable: true` is passed (helpdesk tickets,
  certificate/document requests) — payments and other connectivity-required
  actions leave this false and just fail offline.
- `useSyncStatus` (`lib/client/network.tsx`) auto-flushes the outbox
  whenever the mode leaves Offline, replaying each queued request as a real
  `fetch()` so the server re-authorizes it fresh from the current session
  cookie — nothing about "was this allowed when queued" is trusted.
- **Per-user namespacing** (added during the RBAC work): cache keys and
  outbox entries are tagged with the logged-in `userId`
  (`lib/client/session-store.ts` mirrors it outside React), and switching the
  demo login clears the cache entirely — otherwise switching identities on
  the same device/browser could read back a previous user's cached data.
- Production builds (`npm run build && npm run start`) also register a real
  service worker (`public/sw.js`, registered by
  `components/providers/sw-register.tsx`) for app-shell caching — this is
  skipped in dev to avoid caching HMR bundles.

## Legacy import (lib/importer/, /admin/import)

Adapter interface (`lib/importer/adapters/`) parses CSV/XLSX/JSON into
`{columns, rows}`; `lib/importer/mapping.ts` scores each source column
against `CANONICAL_STUDENT_FIELDS` by string similarity (exact match, prefix/
substring, then token overlap) and greedily assigns unique best matches —
same input/output shape an LLM-based mapper would have, so it's a drop-in
swap later without touching the UI or pipeline. `lib/services/import.ts`
runs upload → validate → commit, reconciling existing students by roll
number instead of duplicating them. Only imports `students` today (no
generic entity import) — adding a new importable entity means a new
canonical-fields list + a new `targetEntity` branch in `import.ts`, following
the same shape.

The RBAC-side "legacy role mapping" (mapping a legacy system's free-text
staff-role labels onto this app's roles) is a *separate*, purely additive
feature — see below — not wired into this student-CSV pipeline.

## RBAC & authorization (lib/rbac/, lib/services/context.ts)

Added on top of the pre-existing prototype (nothing above was rebuilt) to
replace role-string checks (`if (user.role === "admin")`) with a centralized,
scope-aware permission system.

### Mental model

```
USER -> ROLE(S) -> PERMISSIONS -> SCOPE CHECK -> DATA
```

- **Permissions are stable strings** (`resource.action`, e.g.
  `attendance.create`, `exam.results.publish`), defined once in
  `lib/rbac/permissions.ts` (`PERMISSIONS`, `PermissionKey`). This file is the
  only place a new permission key gets invented.
- **Roles are DB rows**, not hardcoded (`roles` / `role_permissions`
  tables). Defaults are seeded from `lib/rbac/seed-data.ts`
  (`ROLE_TEMPLATES`) but fully editable at runtime from `/admin/rbac` —
  adding a brand-new role (e.g. "Placement Coordinator") never touches the
  authorization engine, only assigns it existing permission keys.
- **A user can hold multiple roles** (`user_roles`). Each assignment
  carries an optional explicit `scope` (JSON: `{all:true}` or
  `{departmentId:N}`). If `scope` is `null`, it's resolved *dynamically* from
  the caller's own identity at request time — this is how "student sees only
  their own attendance" and "parent sees only their child's" work with zero
  per-user scope configuration.
- **The single entrypoint is `authorize(ctx, permission, need?)`**
  (`lib/rbac/authorize.ts`, re-exported from `lib/services/context.ts` so
  existing service files didn't need import-path churn):
  1. Checks the caller holds `permission` at all (deny if not).
  2. If `need` (e.g. `{studentId}`, `{courseId}`, `{departmentId}`) is given,
     checks every grant's scope (explicit or dynamically resolved) against it.
  3. Audits every denial; audits successes only when the permission is
     flagged `sensitive` in the catalog (keeps `/admin/rbac`'s audit log
     signal-heavy instead of drowned in routine dashboard reads).
  There's also a non-throwing `can(ctx, permission, need?)` for UI hints
  (nav visibility) — **never use `can()` for an actual security decision**,
  only `authorize()` (throws `AccessDeniedError`, mapped to HTTP 403 by
  `lib/api-helpers.ts`).

### Dynamic scope resolution

When a grant's stored `scope` is `null`, `resolveDynamicScope()` in
`lib/rbac/authorize.ts` derives it from the caller's own linked records:

| `need` shape     | Student           | Parent                          | Faculty                                                             |
|------------------|-------------------|----------------------------------|----------------------------------------------------------------------|
| `{studentId}`    | their own id      | their child (`parents.studentId`) | any student in their course rosters (`sections.facultyId` → programme+semester match) |
| `{courseId}`     | n/a               | n/a                                | any course they teach (`sections.facultyId`)                          |
| `{departmentId}` | n/a               | n/a                                | `ctx.departmentId` (from their faculty/employee record)                |

Results are memoized per-request on `ctx._cache` (a `Map`, server-only,
never serialized).

`resolveStudentIdForAccess(ctx, permission, requestedStudentId?)`
(`lib/services/context.ts`) is what most student-scoped service functions
call — it picks the target student id (explicit, or the caller's own/child
id) and calls `authorize()` under the hood. **Every such function must pass
the specific permission key it's protecting** (this was a deliberate
migration from an older version that didn't differentiate by resource).

### Client-safe vs server-only context

- `ClientContext` (`lib/types.ts`) is sent to the browser: role, name,
  linked ids, `roles: {key,name}[]`, and a flattened, **scope-less**
  `permissions: string[]` for nav/UI hints only.
- `AccessContext` (`lib/rbac/types.ts`) extends that with `grants` (with
  scopes) and `_cache`. Server-only. **Always call `toClientContext(ctx)`
  before `NextResponse.json(ctx)`** — a real bug during development was an
  API route serializing the full `AccessContext` directly (the `_cache` Map
  doesn't even survive JSON serialization).

### Exam-results publish gate

`examResults.graded` (pre-existing column, no migration needed) doubles as
the "published" flag: faculty entering/editing marks sets `graded=false`;
`publishResults()` (Examination Department / admin, permission
`exam.results.publish`) flips it to `true`. Students/parents only ever see
`graded=true` rows — concrete demo of "exam data is highly sensitive."

### AI tool layer + RBAC

Tools in `lib/ai/tools.ts` call into the same permission-checked service
functions the REST API uses — no separate data path. Two real bugs surfaced
and were fixed while wiring this up (worth knowing if you touch this again):

1. `get_student_performance` used to call `riskSvc.getStudentRisk(studentId)`
   directly with **no authorization check** — fixed via
   `riskSvc.getStudentRiskForCaller(ctx, requestedStudentId?)`, which calls
   `resolveStudentIdForAccess` first.
2. A denied tool call returns `{ error: message }` as its "result" —
   `format-tool-result.ts` originally assumed every result had the success
   shape and crashed on this. Fixed with an early
   `if ("error" in result) return EMPTY` guard.

### How to extend

- **New permission**: add one entry to `PERMISSIONS` in
  `lib/rbac/permissions.ts`. Grant it via `ROLE_TEMPLATES` (needs reseed) or
  live from `/admin/rbac` → Roles & Permissions → toggle → Save.
- **New role**: `/admin/rbac` → "New role", check its permissions. No code
  change. Assign it to a user from the Users tab with a scope (own/all/a
  department).
- **New scoped resource type**: extend `Scope`/`ResourceNeed`
  (`lib/rbac/scope.ts`), handle it in `scopeAllows()`, add a dynamic-fallback
  branch in `resolveDynamicScope()` if it should fall back to the caller's
  own identity. The admin UI, audit log, and `can()` are generic and need no
  changes.

### Known gaps (deliberately out of scope)

- No assignments/study-materials feature exists (the spec's
  `assignment.*`/`study_material.*` permissions are catalogued for
  completeness but nothing enforces or renders them — there was never a
  feature there to retrofit).
- Admission Cell is a lightweight "recent admissions + onboard student"
  view, not a full applications/leads pipeline.
- `exam.marks.manage`/`exam.application.manage`/`exam.schedule.manage` are
  granted to the Examination Officer role and appear in the permission
  matrix, but only `exam.results.publish`/`exam.results.manage` (the
  publish-pending list) have real UI behind them.
- The legacy-import role-mapping table (`legacy_role_mappings`,
  `/admin/rbac` → Legacy Import Mapping) is a reference/editable mapping,
  not wired into the student CSV/XLSX pipeline (which only ever imports
  `students`, not staff/user accounts).
