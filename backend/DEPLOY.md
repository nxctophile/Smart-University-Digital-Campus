# Deploying the backend

The backend is a single static-ish binary plus a Postgres database. Nothing
in it talks to AWS, or any other cloud provider, directly - it only needs a
Linux box with a public IP and a `DATABASE_URL`. The two paths below (Docker
on EC2, or a bare binary via systemd) both work unmodified on a plain VPS,
another cloud, or a college's own server room.

## Option A - Docker on an EC2 instance (or any Linux host with Docker)

1. Launch an instance (a `t3.small` or bigger is plenty for this workload),
   open inbound TCP on whatever port you run the backend on (4000 by
   default) in its security group, and SSH in.
2. Install Docker: `curl -fsSL https://get.docker.com | sh`
3. Clone this repo, `cd backend`.
4. `docker compose up -d` - this builds the backend image, starts a
   Postgres 16 container next to it, and runs migrations automatically on
   first boot (see `src/main.rs`).
5. Confirm it's up: `curl http://localhost:4000/healthz`
6. One-time: seed demo data by running the migration script from the repo
   root against this backend's database - see the root README's "Demo
   data" section, or point `DATABASE_URL` at this container's Postgres
   (`postgres://campus:campus@<host>:5432/campus`) and run
   `npm run migrate-demo-data`.
7. On Vercel, set the Next.js project's `BACKEND_URL` env var to
   `http://<ec2-public-ip>:4000` (or put a reverse proxy / load balancer
   with TLS in front of it and point at that instead - recommended for
   anything beyond a demo, since the browser never talks to this URL
   directly but Vercel's own servers do, over the public internet).

To run Postgres separately (e.g. RDS) instead of the bundled container,
skip `docker compose` and just `docker build -t campus-backend . && docker
run -p 4000:4000 -e DATABASE_URL=... campus-backend` - the app doesn't care
where Postgres lives, only that it can reach it.

## Option B - bare binary via systemd (a college's own server)

No Docker required - this is the path for institutions whose IT department
runs a plain Linux server rather than a container platform.

1. Install Postgres 16 (`apt install postgresql` on Debian/Ubuntu) and
   create a database + role matching your `DATABASE_URL`.
2. On a machine with the Rust toolchain (or via a GitHub Actions build),
   `cargo build --release` and copy `target/release/campus-backend` plus
   the `migrations/` folder to the server, e.g. `/opt/campus-backend/`.
3. Copy `.env.example` to `/opt/campus-backend/.env` and fill in
   `DATABASE_URL`.
4. Create a `campus` system user, copy `deploy/campus-backend.service` to
   `/etc/systemd/system/`, then:
   ```
   sudo systemctl daemon-reload
   sudo systemctl enable --now campus-backend
   ```
5. `curl http://localhost:4000/healthz` to confirm it's running; put nginx
   or Caddy in front of it for TLS if it's reachable from outside the
   campus network.

## What you're deploying

- `campus-backend` (or `cargo run`) runs migrations against `DATABASE_URL`
  on every startup - a fresh database gets the full schema automatically,
  no separate migration step.
- Demo data (students, faculty, courses, RBAC roles) isn't generated by the
  backend itself - it's migrated once from the original prototype's seeded
  SQLite snapshot (`data/campus.db` in the repo root) via
  `npm run migrate-demo-data` from the Next.js side. Run it once against
  whatever `DATABASE_URL` the backend is using.
- The frontend (Next.js) is deployed separately, e.g. to Vercel, with its
  `BACKEND_URL` env var pointed at wherever step 6/5 above left this
  backend reachable.
